# Why You Shouldn't Use Firestore Collection Count for Sequential IDs

When generating product codes such as:

```
PRD-000-001
PRD-000-002
PRD-000-003
```

it may seem natural to generate the next code by counting the existing documents.

```ts
const count = (
  await db.collection("products").count().get()
).data().count;

const productCode = `PRD-${String(count + 1).padStart(6, "0")}`;
```

While this works in simple scenarios, **it is not safe in production**.

---

## The Problem: Race Conditions

Imagine there are currently **100 products**.

Two users create a product at nearly the same time.

| Time | User A | User B |
|------|--------|--------|
| 1 | Reads count = 100 | Reads count = 100 |
| 2 | Generates `PRD-000101` | Generates `PRD-000101` |
| 3 | Saves product | Saves product |

Both users generated the same product code because they both read the same count before either document was written.

Result:

```
❌ Duplicate Product Code
PRD-000101
PRD-000101
```

Firestore's aggregation count is only a snapshot of the collection at that moment. It does **not** reserve the next number.

---

# Recommended Solution: Counter Document + Transaction

Instead of counting products, maintain a single document that stores the next available number.

Example:

```
counters/
    products
        nextNumber: 101
```

Whenever a product is created:

1. Start a Firestore transaction.
2. Read `nextNumber`.
3. Generate the product code.
4. Increment `nextNumber`.
5. Save both the updated counter and the new product within the same transaction.

Example:

```ts
const counterRef = db.collection("counters").doc("products");

await db.runTransaction(async (tx) => {
    const counterSnap = await tx.get(counterRef);

    const nextNumber = counterSnap.data()?.nextNumber ?? 1;

    const productCode =
        `PRD-${String(nextNumber).padStart(6, "0")}`;

    tx.update(counterRef, {
        nextNumber: nextNumber + 1,
    });

    const productRef = db.collection("products").doc();

    tx.set(productRef, {
        productCode,
    });
});
```

---

# Why Transactions Prevent Duplicates

Suppose:

```
nextNumber = 101
```

Two users create a product simultaneously.

### User A

- Reads `101`
- Generates `PRD-000101`
- Commits successfully
- Counter becomes `102`

### User B

- Also initially reads `101`
- Firestore detects the counter changed before commit
- Automatically retries the transaction
- Reads `102`
- Generates `PRD-000102`
- Commits successfully

Final result:

```
User A -> PRD-000101
User B -> PRD-000102
```

No duplicates.

---

# Advantages of Using a Counter Document

- ✅ Guarantees unique sequential IDs.
- ✅ Safe when multiple users create products simultaneously.
- ✅ Uses Firestore transactions for consistency.
- ✅ Constant performance regardless of how many products exist.
- ✅ Industry-standard approach for sequential identifiers.

---

# When Is Using the Count Acceptable?

Using the document count is generally acceptable only when there is a single writer, such as:

- One-time data migration
- Import scripts
- Local development
- Admin-only tools where concurrent writes are impossible

It is **not recommended** for public-facing applications or APIs where multiple users or server instances may create products concurrently.

---

# Recommended Firestore Structure

```
counters/
    products
        nextNumber: 1524

products/
    autoGeneratedDocumentId
        productCode: PRD-001523
        name: "Coffee Beans"
        price: 250
```

The Firestore document ID remains an auto-generated ID, while `productCode` serves as the human-readable, sequential identifier.

---

# Conclusion

**Do not generate sequential IDs by counting documents.**

Although it appears simple, counting documents can produce duplicate IDs when multiple requests occur simultaneously.

Using a **counter document with a Firestore transaction** is the recommended approach because it guarantees uniqueness, scales well, and is safe for concurrent writes.
